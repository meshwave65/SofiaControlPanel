### 3. WP26.4 test — technical findings added

Applied the composed skill to the existing WP26.4 matrix and verified the following distinctions against primary sources:

1. **EVM is execution, not consensus.** Ethereum documentation describes EVM execution in the execution client and Proof-of-Stake fork choice/finality in the consensus client. The current MeshWave `mw_append_event` path combines event validation, serialized block creation, hashing and chain-pointer update in the database function, with single-operator consensus in the recorded baseline. Reusing EVM does not by itself decentralize or replace block consensus.
2. **ERC-20 is not a fit for unrestricted UMS semantics.** EIP-20 defines `transfer`, `approve` and `transferFrom`; its standard interface supports direct transfers and delegated spending. Therefore a vanilla ERC-20 does not preserve the approved MeshWave invariant prohibiting direct UMS transfers between MeshWalkers.
3. **Custom restrictions are technically possible but add governance obligations.** OpenZeppelin Contracts v5 documents `_update` as the central customization point for transfers, minting and burning, and its Access Control module supports role-gated operations. A restricted UMS token would need explicit controls over every transfer path, delegated allowances/spenders, mint/burn authority, administrative roles and emergency powers. This is a design possibility, not a recommendation to deploy.
4. **MWN and MW-Ex remain separate responsibilities.** ERC-20 can provide a token interface, but it does not itself implement the MeshWave conversion gateway, asset enablement policy, fiat confirmation, matching, order reservations, ledger reconciliation or product governance. If MWN transferability is intended to be limited to the MW-Ex gateway, that restriction must be explicitly enforced and approved; public transferability must not be inferred from tokenization.
5. **Off-chain responsibilities remain.** EVM smart contracts cannot independently retrieve real-world FIAT confirmation or private MeshWalker data. Those inputs require trusted off-chain processes/oracles and explicit trust boundaries; personal data and private documents remain outside the public chain unless separately justified and approved.

These findings refine the WP26.4 responsibility boundary; they do not select architecture A–F, close WP26.4, or authorize implementation.
