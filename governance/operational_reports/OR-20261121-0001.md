# OperationalReport — OR-20261121-0001

## Objective

Implement context-sensitive Messenger message types and distinguish external origin from semantic message type, without exposing an external option in the user-facing dropdown.

## Inputs, outputs, and tools

- Input: explicit operator request to change the message-type table and the necessary UI/backend flow.
- Repository: `meshwave65/SofiaControlPanel`.
- Mission/task: MISSION_0020 / 20.4.4.
- Supabase project: `ufylccbdjfzydbwhpmpp`, schema `sofia`.
- Outputs: migration `drizzle/0016_message_type_context_and_origin.sql`; schema, database helper, tRPC router, Messenger UI, test fixture, PostgreSQL assertion, CI workflow, and mission progress updates.
- Branch: `feat/message-context-and-origin`.
- Pull request: https://github.com/meshwave65/SofiaControlPanel/pull/33.

## Execution summary

1. Inspected the live `sofia.messageTypes` catalog and the existing `sofia.messages` table. Existing type rows were Instruction, Report, Question, Message, Order, Reply and CreateTask.
2. Added `uiLabel`, `contexts` and `isUserSelectable` to `sofia.messageTypes`.
3. Added `origin` to `sofia.messages`, defaulting to `internal`, with allowed values `internal` and `external`. Existing messages remain classified as internal.
4. Configured the catalog:
   - Message and Question: general and mission.
   - CreateTask: general only.
   - Order and Report: mission only.
   - Reply: general and mission, returned to the UI only when a parent message is selected.
   - Instruction: retained for internal use, not selectable in the UI.
5. Updated the Messenger UI to query the type catalog using its current context and parent-message state. Removed the hard-coded dropdown list.
6. Added backend validation to reject a type that is hidden or unavailable in the selected context, even if a client bypasses the dropdown.
7. Kept origin separate from semantic type. The normal user-facing tRPC routes do not accept an origin supplied by the client. A trusted server-side adapter can call the database helper with `origin: "external"`.
8. Applied migration `message_type_context_and_origin` to the Supabase project. A follow-up query confirmed the seven type records with the intended labels, contexts and visibility. A separate count query confirmed all 32 existing messages remain `internal`.
9. Added the migration to `scripts/ensure-database.mjs`, and added a PostgreSQL fixture/assertion to CI.
10. GitHub Actions run [44914924408](https://github.com/meshwave65/SofiaControlPanel/actions/runs/44914924408) completed successfully: TypeScript check, unit tests, production build, migrations 0010–0016, context/origin SQL assertions, and existing dispatch-boundary tests all passed.

## Problems and workarounds

- The repository's existing message catalog contained both Instruction and Order. The former was retained as an internal non-selectable type; the user-facing Ordem option now maps to Order. No records or types were deleted.
- The database migration was applied to the connected MeshWave65 Supabase project. The Render deployment was not changed, so the new UI/backend code is not yet published.
- The external origin is a data-model capability only. No public external-ingestion endpoint was created because the external identity/authentication contract is a separate security requirement.

## Evidence and uncertainty

- Confirmed by SQL: all seven message types have the configured context and visibility values.
- Confirmed by SQL: `sofia.messages.origin` exists, is non-null and defaults to `internal`; the 32 pre-existing messages are still internal.
- Confirmed by CI: TypeScript, tests, build and PostgreSQL migration suite passed.
- Not verified: authenticated visual QA in the live SCP; Render deployment; actual external-platform ingestion or use of `origin=external`.
- The Supabase security advisor reported an existing INFO finding that `sofia.messageTypes` has RLS enabled without policies. This change did not alter RLS or expose a direct client write path.
