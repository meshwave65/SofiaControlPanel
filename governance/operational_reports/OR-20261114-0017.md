## Production-vs-main code reconciliation — 2026-11-14

### Messenger — direct production defect identified
- At the live production commit 255a016, the messages.create mutation in server/routers.ts only calls db.createMessage(...) and returns the persisted operator message. It does not look up the task, call Manus, invoke the internal LLM, create an assistant reply, or return a response status.
- In current main, the same mutation has been expanded: it validates task ownership, message type and parent-message/task association; persists the operator message; then routes to sendManusMessageAndWait when the task has both agentId and manusTaskId, otherwise invokes the internal LLM; persists an assistant message and returns responseStatus (replied/pending/failed).
- Current main also adds UI handling for processing/replied/pending/failed states and error toasts. The production revision does not have this feedback and displays a success toast immediately after the mutation call is initiated, before the server result is known.
- Therefore, for the currently live production revision, the Messenger cannot converse with Manus or the internal LLM through messages.create; it only stores the operator message. This is a code-level explanation for the reported absence of replies, independent of whether Manus credentials are valid.
- The current main implementation routes to the Manus task associated with the selected mission/agent, not to an arbitrary personal ChatGPT/Manus account session. Direct external-account identity is still not implemented or established.

## Database startup lock-timeout incident — 2026-11-12

- Filtered Render application logs for 2026-11-12 20:20–20:40 UTC returned seven distinct failures of the prestart database initializer at 20:25:30, 20:26:27, 20:27:16, 20:28:20, 20:29:35, 20:31:03, and 20:37:00 UTC.
- Each failure reports: Database initialization failed: PostgresError: canceling statement due to lock timeout. The immediately preceding step is Verify tasks.agentPinned; the failure occurs before the initializer reaches subsequent schema checks.
- The failing deployment was building/running commit 496dd00674522c3fc6a8a724c13dd44dcb835818. Its prestart invokes node scripts/ensure-database.mjs. The exact script blob f6a1132557269541754ad122ca194663876c75ae is identical at commit 496dd, the rollback/live commit 255a016, and current main for the relevant lock behavior.
- The script sets lock_timeout to 15 seconds, then executes ALTER TABLE "sofia"."tasks" ADD COLUMN IF NOT EXISTS "agentPinned" boolean NOT NULL DEFAULT false. PostgreSQL still needs to acquire a table lock to evaluate/execute this DDL; a conflicting lock can therefore cause the observed timeout even if the column already exists.
- The logs prove the failing statement step and repeated timeout, but do not identify the blocking database session/transaction. The blocker and whether it was an active migration, long-running transaction, or another DDL remain unknown.
- Render restarts/retries the prestart sequence after the non-zero exit. The seven failures correlate with the server_failed events on 2026-11-12.
- On 2026-11-14 the rollback/live service later completed startup schema verification and DB connection checks. This establishes that the lock-timeout incident was not continuously preventing startup at the time of the later observation; it does not explain what released the lock or prove the initializer is safe under concurrent startup.

### Updated diagnosis
- **Confirmed incident cause:** startup was aborted because the ensure-database prestart step could not obtain the required lock while verifying/adding tasks.agentPinned within the configured 15-second lock timeout.
- **Unresolved underlying cause:** identity and lifecycle of the blocking lock holder are not available in Render logs. Do not label this as a schema defect or database outage without inspecting pg_locks/pg_stat_activity in a read-only, authorized database session.
- **Risk still present:** current main retains the same lock-timeout/ALTER TABLE approach for agentPinned; current main is not automatically proven safe by the later successful startup.
- **Next diagnostic:** if authorized Supabase read-only access is available, capture pg_stat_activity and pg_locks during a controlled prestart/lock incident; otherwise retain as confirmed timeout with blocker unknown. Do not rerun DDL or alter production to reproduce.
