# OperationalReport — OR-20261117-0005

## Objective

Adicionar à aplicação SofiaControlPanel um adaptador Groq explicitamente selecionável para as chamadas LLM iniciadas pelo servidor/UI do SCP, preservando a Manus Forge como default retrocompatível. Esta mudança não redireciona nem altera o modelo desta conversa Manus.

## Inputs, outputs, and tools

- **Inputs:** esclarecimento do responsável de que deseja separar os caminhos: esta conversa permanece independente e a UI do SCP deve poder usar Groq; confirmação do responsável de que `GROQ_API_KEY` foi criada e salva como segredo no Render (alegação não inspecionada); Blueprint MISSION_0020; quadro de tarefas; código `server/_core/llm.ts`; documentação oficial Groq.
- **Outputs:** `server/_core/env.ts`, `server/_core/llm.ts`, `server/_core/llm.test.ts`; subunidade 20.4.3 e registros canônicos; commit de atribuição `399893f290384b4caff6e646cb5112b677985785`; commit de implementação `bbc32cd468dd22afb16b8e599f16a825e7f5d9d8`; PR #17 atualizada: https://github.com/meshwave65/SofiaControlPanel/pull/17.
- **Skills:** `operational-task-lifecycle` 0.2.0-DRAFT, commit `9db912fcd31561667441addacfcf73d478b28414`; `skill-governance-oracle` 1.1.0 ACTIVE, commit `35ca3757ae5a6a3e602bcabd754c05f7040c5592`.
- **Tools:** Git/GitHub CLI, Vitest, TypeScript, Vite/esbuild; fetch substituído por mock em todos os testes.
- **Documentação consultada:** compatibilidade OpenAI/API Groq [1], modelos suportados [2], tool calling [3], limites de Structured Outputs [4] e parâmetros de raciocínio [5].

## Execution summary

1. Reconciliados o branch `fix/mission-0020-forge-key-error-message`, árvore limpa e PR #17 aberta. A subunidade 20.4.3 foi registrada e comitada antes da edição do código, em commit `399893f`.
2. Acrescentada seleção estrita `LLM_PROVIDER=forge|groq`. Ausência da configuração mantém Forge; valor desconhecido falha sem fallback. Em Groq, a chave é `GROQ_API_KEY`, o endpoint é o oficial `https://api.groq.com/openai/v1/chat/completions`, e o modelo é configurável em `GROQ_MODEL` (default `openai/gpt-oss-120b`). A configuração da Forge e `gemini-2.5-flash` permanecem separadas.
3. Adaptado o payload Groq para `max_completion_tokens` (usa `maxTokens` do caller ou default 4096) e `reasoning_format=hidden`; o campo Forge `thinking` não é enviado. O adapter rejeita combinação de tool calling e Structured Outputs, documentada como não suportada simultaneamente pela Groq [4]. O adapter não lê fallback de uma credencial diferente.
4. Testes mockados cobrem Forge default preservado, endpoint/modelo/header Groq, seleção da chave Groq mesmo quando há uma chave Forge de teste, falha antes da rede se faltar a chave selecionada, ferramenta Groq, incompatibilidade tool+schema e provider desconhecido. Nenhuma chave real foi usada.
5. Validação local: `pnpm test` passou com 11 arquivos/83 testes; refinamento final teve `pnpm exec vitest run server/_core/llm.test.ts` com 6/6 testes. `pnpm check` e `pnpm build` passaram. Build manteve avisos não bloqueantes de bundle acima de 500 kB e `baseline-browser-mapping` desatualizado; pnpm avisou que configurações `pnpm.patchedDependencies` e `pnpm.overrides` foram ignoradas pela configuração/versão local.
6. Os checks do GitHub no commit `bbc32cd` concluíram `SUCCESS`: “TypeScript, tests and production build” e “PostgreSQL migrations 0010–0013 and dispatch boundary”. A PR #17 está `OPEN`, `CLEAN`, sem merge. O título/corpo foram atualizados para descrever o adapter.
7. Não houve chamada à Groq/Forge/Gemini, leitura/verificação do valor de `GROQ_API_KEY`, alteração do Render, deploy, restart, mensagem Messenger real, gravação de dados, migration ou consumo de créditos.

## Problems and workarounds

| Problema | Tratamento | Risco residual |
|---|---|---|
| Apenas salvar `GROQ_API_KEY` não seleciona automaticamente Groq. | Provedor explícito; ativação posterior exige `LLM_PROVIDER=groq`. | Groq documenta incompatibilidade de tool calling com Structured Outputs na mesma chamada. | Guard local falha antes do request; as chamadas atuais de Messenger e plano de ação são separadas. | Fluxos novos que combinem ambos devem ser separados ou redesenhados antes de ativar. |
| A compatibilidade pública não comprova qualidade do GPT-OSS no produto. | CI e testes de payload mockado; sem request real nem avaliação semântica. | Português, qualidade do TR/Blueprint, precisão de tool calls, latência, cotas e custo permanecem sem validação operacional. |

## Evidence and uncertainty

### Fatos verificados

- O código do SCP seleciona por `LLM_PROVIDER`; Forge permanece default; `GROQ_API_KEY` e `GROQ_MODEL` estão mapeados separadamente.
- Os testes mockados confirmam que o request Groq usa sua própria credencial e que a falta dela não usa a credencial Forge.
- Os checks remotos passaram no commit de implementação. A PR #17 continua aberta, sem merge/deploy.
- A documentação Groq consultada lista GPT-OSS 120B/20B com tool use e o endpoint OpenAI-compatible [1] [2] [3]. GPT-OSS 120B é somente um default técnico candidato, não uma validação de superioridade para SOFIA [2].

### Alegações / desconhecidos

- O responsável relata ter criado e salvo `GROQ_API_KEY` como segredo no Render; não se consultou nome/valor remotamente nem se confirmou conta, plano, validade ou cota.
- Não foi confirmado se `LLM_PROVIDER` está configurado no Render. A implementação mantém default `forge`, portanto a chave sozinha não ativa Groq.
- Não foi feita chamada de produção ou teste real via UI, nem avaliação de saída em português, custo, latência, rate limits da organização, retenção/privacidade de dados ou comportamento sob indisponibilidade.
- Esta mudança afeta somente `server/_core/llm.ts` quando o SCP a executar. Não altera o backend usado por esta conversa Manus.
