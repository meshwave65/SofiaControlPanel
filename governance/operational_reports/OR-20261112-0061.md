## Owner clarification

The owner clarified that the contemplated administrative interface is not limited to manual MWN price changes. It is intended to manage multiple economic/system parameters, including:

- UMS-to-MWN parity, currently 1,000 UMS : 1 MWN, with possible future changes.
- Bonus percentage, currently described by the owner as 10%.
- MWN price, currently managed centrally, with possible future automated market/API updates based on supply and demand.
- Other parameters to be identified and classified as the economic model is completed.

The owner expects some parameters to be manually configurable by an administrator and others to be automated. Some may reasonably use a hybrid model (automated calculation with administrative limits/override), subject to explicit policy decisions.

## Architectural recommendation

Treat the administrative interface as an **Economic Parameter Governance Panel**, not merely a price editor.

Each parameter should have an explicit definition and metadata, including:
- Stable parameter key and human-readable description.
- Value, type, unit, precision and validation constraints.
- Update mode: MANUAL, AUTOMATED, or HYBRID.
- Source/authority and permitted writer identity.
- Version, effective-from timestamp and, where applicable, effective-until timestamp.
- Actor/system, reason, approval reference and audit metadata.
- Whether a change requires one-person or additional approval.
- Whether the parameter is snapshotted into transactions or calculations.

All accepted changes should be versioned and auditable. Historical transactions must retain the exact parameter values/versions applied at execution time. A later parity or bonus change must not retroactively rewrite prior ledger entries or transaction outcomes. For calculations spanning multiple parameters, persist the complete applicable parameter snapshot or immutable version references.

Manual administration and automated market/data integrations should use controlled, validated update paths. Automated writers must not bypass parameter-specific bounds, freshness checks, source validation, circuit breakers, or any approval/override policy adopted for that parameter. The UI is a control surface; the authoritative parameter state and history remain in the backend/database governance layer.

The current price and its history can be one parameter family within this broader framework. Price ingestion from a market API should converge on the same controlled update mechanism used by the administrative interface, while retaining source/time/provenance.

## Decisions and open gates

- **Confirmed by owner:** administrative governance covers multiple parameters, not only price; parity and bonus are examples; some parameters will be manually configurable and others automated.
- **Recommended:** common versioned parameter registry/history with parameter-specific policies and controlled writers; immutable transaction snapshots.
- **Still open:** complete parameter inventory; meaning/base/eligibility of the 10% bonus; exact parity conversion/rounding/residue rules for future parity changes; authorization and approval matrix; effective-time semantics; automated-source contracts and safeguards; administrative page placement.
- **Required next investigation:** trace existing parameter storage and consumption across canonical Supabase project `ufylccbdjfzydbwhpmpp`, application repositories, SQL functions, backend services, and MW-Ex. Identify which parameters already exist, their actual consumers/writers, and whether transaction records preserve applied values.
