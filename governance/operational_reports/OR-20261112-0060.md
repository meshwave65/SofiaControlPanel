# OR-20261112-0060 — Canonical MWN price source and dual-mode price governance

- **Mission:** MISSION_0021
- **Task:** 21.5 — MWN internal price source/history (continuity)
- **Date:** 2026-11-12
- **Status:** SUBMITTED
- **Scope:** Documentary clarification and architectural recommendation only
- **Database/code changes:** None

## Owner clarification

The owner clarified that the original decision to use `mwc_sale_prices` was a point-in-time architectural choice: establish one canonical, centrally maintained value for the price so the entire system can consume it without hardcoded copies.

The table should therefore not be classified as exclusively legacy solely because its name/columns refer to MWC. Its current semantic role in all consumers still needs code-path verification.

The owner is open to suggestions on whether the price-history structure should also become the canonical source of the current value.

The only implementation-location decision currently made is that price management needs a central administrative capability, potentially an administrative page. The owner expects two modes:
1. Manual price changes made by an authorized administrator.
2. Future automated updates through a market-connected API, where real supply/demand fluctuations determine the current price and feed the same centrally managed/observable system.

## Architectural recommendation

Adopt one canonical price state with a single authoritative write path, and an append-only event history. The history should record every accepted price transition, including old/new value, effective/recorded timestamps, origin (manual or market API), actor/system identity, source reference, and relevant reason/market context.

The current price exposed to the rest of the system should be derived from or transactionally synchronized with that history, rather than maintained as an independently editable duplicate. Manual administration and automated market ingestion should call the same validated price-update service/RPC so that validation, authorization, atomicity, audit metadata, and downstream publication are consistent.

A practical implementation can retain a compact current-value row/cache for fast reads, provided it is updated atomically with the append-only history and is explicitly treated as a projection, not a second source of truth. Existing `mwc_sale_prices` may be retained and evolved if code-path and schema review confirms it can safely serve this role; otherwise introduce a canonical MWN price-state abstraction and migrate consumers deliberately. Do not rename or remove legacy objects as part of this investigation.

The administrative interface is a management surface, not the authority itself. The API integration is a future input adapter, not a separate pricing authority. Both must converge on the same canonical update path.

## Decisions and open gates

- **Confirmed by owner:** centralized canonical price value; no hardcoded price copies; manual administrative adjustment; future market API automation based on supply/demand.
- **Recommended, not yet approved as implementation detail:** append-only price event history as authoritative record; shared update path for manual and automated changes; current-price projection/cache only if needed.
- **Still open:** exact admin page/location; market venue/API and market-data contract; price formation rules, validation bounds and stale/outage behavior; authorization/approval policy; effective timezone/clock semantics; exact schema and update mechanism.
- **Required next investigation:** trace all readers and writers of `mwc_sale_prices` and any MWN price fields through application repositories, backend services, SQL functions, triggers, scheduled jobs, and deployed endpoints. Establish whether the existing table already supplies the canonical price to MW-Ex and other system components before proposing schema changes.

## Safety boundary

This OR records architectural intent and a recommendation. It does not authorize DDL, data updates, price changes, market API connection, administrative UI implementation, deployment, or any financial operation. No Supabase data or production system was modified.
